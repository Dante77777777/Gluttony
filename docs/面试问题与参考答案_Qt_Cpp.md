### 02 Gluttony 和 Lust 的端到端数据流是什么？

**参考回答**

Lust 侧从相机取得图像，必要时做格式转换和 JPEG 编码，生成包含序列号、时间戳、尺寸、像素格式和 payload 长度的协议帧，再通过 TCP 发送。Gluttony 解析字节流、解码 JPEG，将帧送给推理工作线程；OpenVINO 返回图像分数、异常图和 mask，客户端按阈值生成 OK/REVIEW/NG，显示热力图，并可持久化检测记录。若响应返回 Lust，则用 sequence 关联原始请求。传输层解决字节流边界，业务层解决请求与响应的关联。

**严厉追问**

请在白板上画出线程边界、队列和错误返回路径。断线发生时，哪一端负责清理未完成请求？

**追问答题要点**

## 二 Gluttony 异常检测与部署

### 03 PatchCore 从训练图像到检测结果的原理是什么？

**参考回答**

项目使用 ImageNet 预训练的 wide_resnet50_2 提取中间层特征，配置使用 layer2 和 layer3。PatchCore 将局部 patch 特征组织成正常特征 memory bank；coreset 采样保留能代表特征分布的子集，降低存储和最近邻搜索开销。推理时提取同样形式的 patch 特征，计算它们到 memory bank 的最近邻距离，距离可形成空间异常图；异常图经上采样得到像素热力图，模型同时输出图像级 pred_score。项目把这段具体计算交给 Anomalib 的 Patchcore 实现，简历不应把它说成我从零实现的算法。

**严厉追问**

你使用的采样比例是多少？配置中是 0.01。这个比例对精度、内存和速度有什么影响？你做过哪些对照实验？

**追问答题要点**

配置为 0.01。降低比例可降低 memory bank 存储和近邻检索开销，但可能丢失少见正常模式，导致误报或漏检变化。必须在同一数据划分、硬件和预处理下做比例对照，报告精度、耗时和峰值内存；未做实验就明确说这是当前配置值。

### 04 为什么 PatchCore 的 memory bank 主要由正常样本构成？

**参考回答**

这是无监督/一类异常检测的思路：先学习“正常外观”的特征分布。测试 patch 若接近正常特征库，距离较小；若远离正常特征，距离较大，作为异常候选。训练时混入缺陷样本会把部分异常也纳入“正常参考”，削弱距离信号。实际评估仍需要带缺陷标注的测试集，检查图像级和像素级检测效果。

**严厉追问**

MVTec AD 的 train、test、ground_truth 分别承担什么作用？若训练集中混入少量缺陷，你会如何发现和处理？

**追问答题要点**

MVTec train 提供正常训练图像；test 包含正常和异常图像，用于评估；ground_truth 提供缺陷区域标注，用于像素级评估。若训练集可能混入缺陷，应先做数据审计/抽检与异常样本筛查，再隔离或清洗，并记录规则，不能把测试集拿来调参。

### 05 为什么选 wide_resnet50_2 的 layer2 和 layer3？

**参考回答**

浅层保留较多纹理和边缘信息，深层包含更抽象的语义信息；组合不同层能兼顾局部纹理异常和较大结构异常。项目配置确实指定了 wide_resnet50_2、layer2、layer3，但“为什么它在我的数据上最优”需要实验支持，不能仅凭架构名称断言。应比较单层/多层、不同 backbone 的 AUROC、像素级指标、推理时间和内存。

**严厉追问**

如果 layer2、layer3 的特征网格尺寸不同，如何对齐或融合？你项目里具体使用了 Anomalib 哪个版本和实现？

**追问答题要点**

layer2、layer3 空间分辨率可能不同，模型通常需要将特征映射到可比较的网格并进行融合；本项目把融合细节交给 Anomalib Patchcore。回答具体版本和融合实现前，应查看当前环境版本和模型源码，不要把通用原理说成自己实现。

### 06 coreset sampling 解决什么问题？1% 是怎么确定的？

**参考回答**

全部正常 patch 特征可能形成很大的 memory bank，导致内存占用和最近邻搜索成本偏高。coreset 试图用较小的代表性子集覆盖原始特征空间。当前配置 sampling ratio 是 0.01，即采样比例参数设为 1%；它是配置选择，不等于我已证明它是最优值。正确做法是在固定数据划分和硬件条件下比较多个比例，并报告精度、峰值内存和延迟。

**严厉追问**

如果 coreset 过小，容易漏掉哪些正常模式？如果过大，瓶颈会落在哪里？

**追问答题要点**

过小的 coreset 可能漏掉长尾正常纹理/姿态，过大则增加内存和最近邻搜索成本。应做比例消融实验；当前配置的 1% 只能作为工程参数陈述。

### 07 你如何评估模型，如何选 OK/REVIEW/NG 阈值？

**参考回答**

先区分图像级和像素级评估：图像级关注一张图是否异常，像素级关注缺陷区域定位；常见指标可包括 image AUROC、pixel AUROC，以及适合工业漏检/误报权衡的指标。阈值不能凭感觉设，应在独立验证集上按业务代价选择，例如优先约束漏检率，再设置复核区间。客户端目前按 reviewThreshold 和 ngThreshold 分成 OK、REVIEW、NG；阈值应和具体模型、类别、数据分布绑定。

**严厉追问**

请给出你实际跑出的指标、数据划分和阈值。如果现在没有这些数字，你会如何在面试中诚实说明？

**追问答题要点**

先给出数据划分、类别、指标、阈值和混淆矩阵。如果当前没有可信数字，直接说“目前实现了训练、评估和阈值流程，但我还没有完成足够的多轮对照压测，不能给出稳定的泛化结论”，并提出补测计划。

### 08 Python 导出的模型如何在 C++/OpenVINO 里保持预处理一致？

**参考回答**

需要核对输入尺寸、NCHW/NHWC、通道顺序、数据类型、像素范围、均值方差归一化和 resize/crop 策略。当前 C++ 推理代码将输入转为 RGB888、缩放到模型尺寸、转成 float32 并按 0 到 1 写入 NCHW；模型加载时检查单输入、4 维、3 通道、静态宽高和 f32。部署前必须确认导出模型是否已内嵌预处理，避免重复或遗漏归一化。

**严厉追问**

你当前代码使用 IgnoreAspectRatio，会不会拉伸图像？训练预处理和部署预处理是否完全一致？你如何验证？

**追问答题要点**

逐项固定一组图片，在 Python 训练/导出侧和 C++ 侧比较预处理张量及模型输出；检查颜色顺序、resize、像素范围、均值方差、布局和输出误差。当前 IgnoreAspectRatio 会改变长宽比，只有训练预处理一致或模型接受该变形时才合理；需要用样本验证并考虑 letterbox/crop。

### 09 为什么同时支持 OpenVINO IR 和 ONNX？部署时有什么风险？

**参考回答**

两种格式便于接入不同导出产物；客户端都由 OpenVINO Runtime 读取和编译，因此不需要额外链接 ONNX Runtime。IR 通常由 XML 描述结构并配套 BIN 权重。风险在于不同导出格式可能有不同输出节点名称、预处理封装、动态 shape 和算子兼容性；应对输入输出 shape/type/name 做校验，并用同一组图片比较 Python 与 C++ 的 score、mask 和热力图。

**严厉追问**

当前代码固定读取 pred_score、anomaly_map、pred_mask。若导出模型的输出名称变化，程序会怎样？你会如何改进？

**追问答题要点**

如果输出节点名称变了，按固定名称读取会抛异常/推理失败。可在加载时枚举输出 tensor 的名称、类型和 shape，按元数据或显式模型契约绑定，并在启动时验证必需输出。

### 10 图像级分数、热力图和缺陷面积分别是什么？

**参考回答**

图像级分数是整张图的异常程度，客户端和两个阈值比较后输出 OK/REVIEW/NG。anomaly_map 是空间异常响应，代码将其归一化、着色并缩放到原图尺寸后叠加显示。pred_mask 是二值区域，代码用最近邻插值放大后统计非零像素，得到缺陷像素面积。它不是物理面积；若要 mm²，需要相机标定、像素尺寸和视野位置等信息。

**严厉追问**

热力图的 min-max 归一化会造成什么误导？不同图像的颜色能直接比较吗？如何避免把显示色阶当成模型分数？

**追问答题要点**

min-max 归一化会把每张图自己的最小值和最大值映射到同一色阶，适合单张可视化，但颜色不能直接跨图比较，也可能把低幅噪声显示得很显眼。比较时应展示原始 score/固定色标，区分 UI 可视化与定量判定。

### 11 OpenVINO 推理线程如何管理 InferRequest 和模型生命周期？

**参考回答**

模型加载阶段读取并编译模型，推理时创建 InferRequest、设置输入 tensor、执行同步 infer，再读取输出 tensor。若多个线程同时推理，需明确 InferRequest 是否独立、模型是否共享安全；一般每个并发 worker 使用独立 InferRequest，避免共享可变请求状态。当前项目把推理放进 worker 线程以免阻塞界面，停止流程要等待线程退出，不能在请求仍执行时释放模型资源。

**严厉追问**

你当前的 InferRequest 是每张图新建还是复用？为什么？模型切换时如何防止旧请求结果回写到新会话？

**追问答题要点**

当前代码每次 inferImage 创建 InferRequest；这简化并发隔离，但可能有分配开销。是否复用应由性能测量决定，复用时要保证请求不被并发共享。切换模型可用 generation/session token 丢弃旧会话回调，并等待旧 worker 退出后再释放资源。

### 12 你如何解释“实时推理”？请给出可核验的性能数据。

**参考回答**

“实时”必须绑定硬件、图像尺寸、模型、batch、预热方式和统计口径。应分别记录预处理、推理、后处理、网络传输和端到端延迟，至少报告多轮的中位数和高分位数，并同时说明帧率、丢帧策略和内存。没有完整压测数据时，我会说目前实现了异步处理和实时数据流路径，但不宣称已达到某个工业节拍。

你简历没有列延迟数字。面试官问“你怎么证明实时”，你能拿出什么日志或测试结果？

**追问答题要点**

## 三 Lust 相机采集与 TCP 联动

### 13 CameraInterface、CameraFactory、CameraContext 分别解决什么问题？

**参考回答**

CameraInterface 统一枚举后相机对象需要提供的连接、采集、参数读写和取图接口；CameraFactory 根据厂商信息创建具体实现；CameraContext 负责集中管理当前相机上下文和生命周期。这样 UI/业务代码依赖抽象接口，避免散落厂商判断。但工厂模式不能自动带来硬件兼容，必须有已注册并验证过的具体实现。当前工厂代码注册 VirtualCamera；海康支持只能按实际接入状态表述。

**严厉追问**

抽象接口中返回 uint32_t 错误码有什么利弊？CameraInterface 的析构函数为什么需要 virtual？

**追问答题要点**

uint32_t 能携带 SDK 风格错误码，调用方可分支处理；缺点是语义不直观、容易漏检错误码，可改为 enum class/expected 风格结果。抽象类经基类指针删除派生对象时需要 virtual 析构，否则行为未定义且资源可能泄漏。

### 14 你说支持多相机，当前代码到底支持到什么程度？

**参考回答**

严谨说法是：项目已经建立相机抽象和工厂扩展点，并提供虚拟相机用于无硬件联调；当前工厂注册了 VirtualCamera。若海康相机实现尚未接入工厂或未使用真实设备验证，就只能说预留适配，不应说多品牌相机已经可用。面试中我会明确已经完成的部分、未完成的部分和下一步验收标准。

**严厉追问**

假设现在要求你新增海康相机，哪些文件或模块需要实现？如何验证 acquire/connect/startGrabbing/stopGrabbing 的生命周期？

**追问答题要点**

新增厂商实现 CameraInterface 的纯虚接口，在 CameraFactory 注册 creator，在必要处实现参数映射和配置转换；验证资源状态机和失败回滚：acquire 后才能 connect，建立 stream 后才能 start，stop 后销毁 stream，再 disconnect/release。要用虚拟相机单测和真实设备联调分别验收。

### 15 JSON 驱动的相机参数树怎么工作？

**参考回答**

JSON 描述参数名称、分组、类型、范围、枚举项和提示信息；解析层把描述转成参数节点；CameraParamModel 通过 Qt Model/View 接口提供行列、父子关系、显示值和编辑角色；delegate 根据参数类型创建布尔、数值、枚举、字符串或命令控件，并把编辑结果写回 model。这样新增参数类型时不必为每个参数重复写整套界面。

**严厉追问**

Qt 的 DisplayRole、EditRole、flags 和 setData 分别负责什么？参数写入设备失败时，模型里的值如何回滚或显示错误？

**追问答题要点**

DisplayRole 提供展示文本，EditRole 提供编辑值；flags 声明可否编辑；setData 校验新值并发 dataChanged。写设备失败时要保留旧值或恢复旧值，并显示错误，不能让 UI 看似成功而硬件未改变。

### 16 TCP 为什么会出现粘包和半包？你如何处理？

**参考回答**

TCP 提供有序字节流，不保留应用层 send/write 的消息边界。一次 readyRead 可能只有半个帧，也可能包含多个帧。接收端把新字节追加到 buffer，先检查固定帧头和 payload 长度；完整帧就解码并从 buffer 移除，再循环解析后续粘连帧；数据不足则保留，等待下次追加。不能把一次 readAll 当成一个完整业务包。

**严厉追问**

如果长度字段是恶意的超大值，如何防止分配巨量内存？如果 magic 错了，当前实现会如何处理，能否自动重新同步？

**追问答题要点**

当前 decoder 遇到 InvalidData 会清空缓存并发协议错误，不做 magic 字节级重同步；若网络流可能从任意位置恢复，可设计有限长度扫描 magic 并校验 version/header/size，或直接断开重连，避免错误数据无限解析。长度上限必须在等待 payload 或分配前检查。

### 17 请逐字段解释你们的 40 字节帧头。

**参考回答**

协议头固定 40 字节，采用大端序：magic 4 字节，version 2 字节，header size 2 字节，message type 2 字节，pixel format 2 字节，sequence 8 字节，timestamp 8 字节，width 4 字节，height 4 字节，payload size 4 字节。magic 是 LUST，version 当前为 1；单帧 payload 上限 64 MiB。头部固定长度和显式字节序让两端不依赖编译器结构体对齐。

**严厉追问**

为什么不能直接把 C++ struct 内存 memcpy 到 socket？升级协议版本时如何兼容旧客户端？

**追问答题要点**

结构体存在 padding、对齐、主机字节序和 ABI 差异，直接 memcpy 会导致跨平台 wire format 不稳定。当前协议显式逐字段编码为大端字节序。升级可增加版本和能力协商，保留旧解析器或做向后兼容字段规则。

### 18 序列号如何避免推理结果串帧？超时和重复响应怎么处理？

**参考回答**

每个图像请求带单调递增 sequence，发送前在 tracker 中记录开始时间；响应解码后按 sequence 查找请求并完成对应项，不能按响应到达顺序配对。tracker 会区分重复请求、未知响应、超时和容量超限；当前默认超时 5 秒、最多 512 个 pending。超时后移除记录，迟到响应应作为未知响应处理并记录。

**严厉追问**

如果连接断开后 sequence 从 1 重新开始，如何避免旧会话的迟到响应匹配新请求？是否需要 session id？

**追问答题要点**

增加 session_id 或连接代次，并用 (session_id, sequence) 作为请求键；重连时清空旧 tracker，拒绝旧会话响应。产品级 exactly-once 还需要持久化唯一请求 ID 和幂等处理，单靠 TCP sequence 不够。

### 19 Lust 的 CameraImageQueue 为什么有界？满队列和停机时怎么办？

**参考回答**

图像帧通常很大，无界队列会在采集快于处理时持续占用内存并增加延迟。有界队列能明确背压策略；队列通过互斥量保护读写，用 condition_variable 等待 not-empty/not-full，并提供 shutdown 唤醒阻塞线程。应根据实时检测语义选择阻塞采集、丢旧帧或丢新帧，并统计丢帧。具体策略要以 push/pop 的实现和测试为准，不能只凭类名断言。

**严厉追问**

生产者永久快于消费者时，阻塞策略会带来什么后果？工业检测到底应该丢帧还是停线？取决于什么业务条件？

**追问答题要点**

生产快于消费时阻塞可以保留每帧但会让 SDK 缓冲或相机端积压，产生延迟；丢帧适合预览但不适合逐件质检；达到容量时停采/报警适合不允许漏检的产线。要由业务的漏检代价、相机触发方式、缓冲能力和节拍决定。

### 20 Gluttony 的 latest-only 策略有什么取舍？

**参考回答**

当前推理 controller 同一时刻最多处理一帧，并保留至多一帧待处理；新帧到来时会替换旧的 pending frame，并增加 dropped counter。优点是避免队列无限积压，让显示结果尽量接近最新画面；代价是中间帧会被主动丢弃。因此只能说“结果按 sequence 关联，避免串帧；过载时显式丢弃旧待处理帧”，不能说“高帧率下绝不丢帧”。若业务要求每件产品都必须检测，需要产品 ID、完整队列、背压或停线机制。

**严厉追问**

如果每帧代表一件产品，latest-only 设计为什么不合格？你会怎样改成可追溯且不静默丢失的流程？

**追问答题要点**

若每帧对应一件产品，必须以 product_id/request_id 贯穿采集、推理和结果落库，不能覆盖 pending 帧。队列需有上限和明确满队列动作（背压、停线/报警或持久化缓冲），每个产品有终态；重试要幂等，并有账实核对。

### 21 TCP 客户端发送时如何做背压？write 成功是否代表对端收到？

**参考回答**

write 成功仅表示数据被 Qt 接受进入发送缓冲，并不等于对端已收到或处理。Lust 通过 bytesToWrite 检查待发送字节数并设置上限，避免无限堆积；如果一次 packet 只接受部分数据，当前实现选择 abort 连接，防止继续发送导致应用层包内容不完整。bytesWritten 表示缓冲进度，不是业务 ACK；若需要确认对端处理，必须有协议级响应。

**严厉追问**

断线重连时，未确认的帧是否重发？如何保证重试幂等，避免重复落库或重复判定？

**追问答题要点**

重连重发需要应用层 ACK 和幂等键；服务端以 session/request id 做唯一约束，重复请求返回已存结果而不是重复执行副作用。没收到 ACK 的请求要标为不确定状态，不能默认为失败或成功。

### 22 图像从 OpenCV 到 Qt 时，怎么处理通道、stride 和内存生命周期？

**参考回答**

cv::Mat 可能是 BGR、带行步长且引用计数管理；QImage 的格式和每行 bytesPerLine 也需要显式处理。构造 QImage 时必须提供正确 stride，通道顺序要转换；如果 QImage 只是引用 Mat 的外部内存，底层缓冲区释放后会悬空，因此需要在跨线程或长期保存时深拷贝，或保证共享数据生命周期覆盖使用期。不能假设每行都等于 width × channels。

**严厉追问**

一个 ROI cv::Mat 可能不是连续内存，你的转换代码能否处理？QImage::copy() 在这里解决什么问题？

**追问答题要点**

ROI Mat 可能非连续，按行读取时用 ptr(y) 和 step，而不是假设连续平铺；QImage 构造必须提供 bytesPerLine。QImage::copy() 让图像拥有独立存储，避免外部 Mat 缓冲区释放后悬空，代价是一次复制。

### 23 Lust 参数 Model/Delegate 相比直接堆 QWidget 有什么好处？

**参考回答**

Model 保存参数数据及层级关系，View 负责展示，Delegate 按参数类型创建编辑器并提交修改。分离数据、展示和编辑逻辑后，参数多时不会为每个单元格长期保留大量控件，也更容易统一校验和扩展类型。对于命令型参数，还要处理触发动作与普通值编辑不同的问题。

**严厉追问**

编辑器什么时候创建、何时提交？如果设备参数写失败，如何保持 UI 与硬件状态一致？

**追问答题要点**

编辑器由 delegate 在编辑时创建，提交后通过 setModelData 写回 model；校验在 model/业务层执行。设备写入失败应返回错误并恢复旧显示值或标记未同步状态，必要时重新读硬件当前值。

## 四 Qt C++ 并发与工程基础

### 24 Qt 的 AutoConnection 在跨线程时做什么？

**参考回答**

AutoConnection 在发射信号时比较发射线程与接收对象 affinity 所在线程：同线程通常直接调用，跨线程则排入接收线程事件队列，槽函数要等该线程事件循环处理。接收对象的线程亲和性和事件循环必须正确；跨线程传递自定义类型时，queued connection 可能需要注册元类型。UI 对象只能在 GUI 线程更新。

**严厉追问**

把一个 QObject moveToThread 后，哪些对象不能再直接从原线程调用？如果线程没有事件循环，queued slot 会怎样？

**追问答题要点**

QObject 的方法直接调用不会因为 moveToThread 自动变成跨线程安全调用；跨线程要用 queued signal/slot 或 invokeMethod。queued slot 依赖接收线程事件循环运行，否则事件无法及时处理。UI 更新始终排队回 GUI 线程。

### 25 QThread 子类和 worker-object 模式各适合什么情况？

**参考回答**

QThread 对象本身通常仍属于创建它的线程；run() 才在新线程执行。短小且不需要事件驱动槽的任务可以重写 run；需要 queued slot、timer 或 socket 等事件循环能力时，常用 worker QObject moveToThread。项目中两种模式要按实际模块说明：Gluttony 推理 worker 使用 moveToThread，Lust 的 AcquireImageProcess 是项目自己的采集线程实现。停止时要发出退出信号、唤醒阻塞等待并 join/wait，不能强杀线程。

**严厉追问**

你项目里的采集循环阻塞在哪里？stop 时如何确保线程不会永远卡在 condition_variable 或 SDK 取图调用？

**追问答题要点**

采集线程应有停止标志，并让阻塞队列 shutdown/wakeAll；SDK 取图应设置超时或使用 SDK 停流打断。退出顺序是请求停止、停止硬件流、唤醒等待、等待线程结束、再释放相机对象；不能 terminate 强杀。

### 26 RAII 如何减少并发和资源管理错误？

**参考回答**

RAII 把资源生命周期绑定到对象生命周期：构造时获取锁、文件或句柄，析构时释放。这样异常或提前 return 时仍能清理资源。锁应使用 lock_guard/unique_lock，线程对象、socket、数据库连接等也应明确所有权和销毁线程。RAII 不能代替并发设计，但能降低忘记 unlock/close 的风险。

**严厉追问**

lock_guard 和 unique_lock 有何区别？条件变量为什么通常配合 unique_lock 和谓词循环？

**追问答题要点**

lock_guard 作用域内自动加锁解锁；unique_lock 可延迟加锁、手动 unlock/relock，适合 condition_variable。wait 要用谓词重检，因为可能虚假唤醒，也避免丢失状态变化。

### 27 unique_ptr、shared_ptr、weak_ptr 如何选择？

**参考回答**

默认优先 unique_ptr 表达唯一所有权；只有多个对象确实共享生命周期时才使用 shared_ptr；观察 shared_ptr 管理对象但不延长其生命周期时用 weak_ptr，避免循环引用。Qt QObject 父子对象树也会管理生命周期，不能再盲目叠加智能指针造成双重释放。接口返回裸指针时，应先说明由谁拥有、在哪个线程销毁。

**严厉追问**

如果 A 持有 B 的 shared_ptr，B 也持有 A 的 shared_ptr，会发生什么？在 Qt QObject 场景如何处理？

**追问答题要点**

shared_ptr 环引用会让引用计数始终不归零，对象不能析构。将其中一个方向改成 weak_ptr 或改为非拥有观察指针。QObject 父子对象已有所有权树时，应遵守单一清晰的销毁责任。

### 28 互斥量、信号量和条件变量有什么区别？

**参考回答**

互斥量保护共享状态的临界区；信号量维护可用资源计数，适合限制并发数量或表示计数型资源；条件变量让线程等待某个共享谓词成立，通常与 mutex 配合。条件变量可能虚假唤醒，所以要在锁内循环检查谓词。选择依据是要保护数据、计数资源还是等待状态变化。

**严厉追问**

请用 CameraImageQueue 的 notEmpty/notFull 解释生产者消费者的完整唤醒过程。

**追问答题要点**

生产者持锁检查队列未满，不满则 push 并 notify notEmpty；消费者等待 notEmpty 谓词，醒来后取出并 notify notFull。shutdown 要在锁保护下更新状态并通知所有等待者，等待方醒来后检查 shutdown 并退出。

### 29 SQLite migration 为什么要有 checksum 和事务？

**参考回答**

迁移表记录版本、名称、checksum 和应用时间；启动时比较数据库 user_version 与迁移目录，检查已应用迁移是否被改写，并按版本顺序执行。每个迁移在事务中执行，任一 SQL 或后置校验失败就回滚，避免 schema 处于半迁移状态。application_id 可帮助确认数据库归属。事务保证原子性，checksum 检查迁移内容一致性；二者作用不同。

**严厉追问**

如果已经应用的 migration 文件被开发者修改了，启动时应如何处理？为什么不能直接把 user_version 改大？

**追问答题要点**

已应用 migration 的 checksum 不匹配意味着历史脚本被改动或数据库与程序不匹配，应报错并要求人工迁移/修复，不可静默重跑。user_version 只是版本标记，不代表 migration SQL 已原子成功执行。

### 30 你怎样证明项目质量，而不只说“写了测试”？

**参考回答**

针对协议模块测试固定 wire format、字段边界、非法 magic/version、半包、粘包和超长 payload；针对 tracker 测试乱序、重复、未知和超时；针对 queue 测试满/空、shutdown 和并发行为；推理层用固定输入比较 Python 与 C++ 的输出；持久化测试迁移失败回滚与重启恢复。报告测试覆盖的边界和未覆盖范围，不把单元测试通过说成生产可靠性证明。

**严厉追问**

你亲自写过的最有价值的一个测试是什么？它曾经抓到什么 bug？

**追问答题要点**

选择协议/队列/tracker 的一个实际测试，讲清测试输入、预期行为、曾捕捉的问题和回归保护。测试结果要对应提交和环境；当前项目有哪些 CTest 名称可从 CMake/测试目录核实，别说没跑过的测试通过。

### 31 TCP 和 UDP 如何选？工业图像传输为什么选 TCP？

**参考回答**

TCP 是可靠、有序的字节流，适合需要完整帧、可靠交付和统一结果关联的场景；代价是重传和队头阻塞。UDP 保留数据报边界、时延可控，但应用需要自己处理丢包、乱序、重传和拥塞。项目选择 TCP 后，仍然要自己定义应用层帧格式，因为 TCP 不保留消息边界。若业务更重视低延迟且允许丢帧，可以评估 UDP/RTP 或其他传输方案。

**严厉追问**

如果 TCP 连接很稳定但延迟越来越大，你会检查哪些队列和缓冲区？

**追问答题要点**

先看 bytesToWrite、应用层待发队列、采集队列和推理队列的水位，再看发送/推理耗时、网络带宽和接收端处理能力。TCP 的重传/队头阻塞会让后续数据等待，因此要有上限、背压策略和端到端延迟监控。
