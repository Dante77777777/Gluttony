# Gluttony 检测数据持久化需求与概要设计

## 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 需求已确认，待数据库结构设计 |
| 适用版本 | 数据持久化第一阶段 |
| 目标客户端 | C++ / Qt 单机客户端 |
| 推荐数据库 | SQLite |
| 大文件存储 | 本地文件系统 |
| 更新时间 | 2026-07-23 |

## 1. 背景

Gluttony 当前能够使用 OpenVINO Runtime 加载 OpenVINO IR 或 ONNX 模型，对单张图片或文件夹中的图片执行异常检测，并在客户端中展示以下结果：

- 原始图片
- 热力图
- OK、REVIEW、NG 判定
- 异常分数
- 推理耗时
- 缺陷面积

当前检测结果主要服务于本次程序运行。当检测图片数量较大时，如果每条检测记录长期持有完整的原图或热力图 `QImage`，内存占用会随着检测数量不断增长。同时，用户需要主动选择是否将某次检测保存为可长期查看的历史记录。

因此，需要为项目增加一套同时覆盖数据库、文件存储、草稿管理、异常恢复和重复保存控制的数据持久化方案。

## 2. 设计目标

第一阶段需要实现以下目标：

1. 每张图片检测完成后立即持久化，不等待整个批次完成。
2. 大量图片检测时，不在内存中长期保存所有完整热力图。
3. 用户可以将一次检测确认为正式历史记录。
4. 用户重复保存同一个检测批次时，不产生重复数据。
5. 用户重新检测同一批图片时，保留为一次新的检测历史。
6. 程序异常退出后，已经完成的检测结果可以被识别和恢复。
7. 用户可以查看已保存批次的汇总信息和逐图结果。
8. 用户可以主动放弃未保存草稿，并清理关联的临时数据。
9. 中断批次可以按照原始输入顺序继续检测。
10. 用户可以从磁盘选择已保存的批次并载入查看。

## 3. 非目标

第一阶段暂不包含以下内容：

- 多用户账号与权限控制
- 客户端之间的数据同步
- 中央数据库服务器
- 云端对象存储
- 检测任务的跨设备调度
- 原图的内容寻址存储与自动去重
- 数据加密、审计签名和合规归档

以上能力可以在本地持久化流程稳定后逐步扩展。

## 4. 第一阶段关键决策

| 问题 | 第一阶段决策 |
|---|---|
| 使用什么数据库 | SQLite |
| 图片是否直接存入数据库 | 否 |
| 原图和热力图存在哪里 | 程序管理的本地文件目录 |
| 何时写入检测结果 | 每张图片检测完成后 |
| 什么是一个检测批次 | 用户一次点击“开始检测”产生的任务 |
| 何时生成批次 ID | 检测开始时 |
| 用户点击“保存”做什么 | 将批次从草稿状态变为正式保存状态 |
| 重复点击“保存” | 不新增批次，不重复插入检测条目 |
| 重新检测相同图片 | 创建新的检测批次 |
| 草稿是否写入磁盘 | 是 |
| 主动放弃草稿 | 删除草稿记录及其关联文件 |
| 程序异常退出 | 保留已有结果，标记为中断批次 |
| 未保存草稿保留时间 | 不跨会话保留，用户不保存时直接删除 |
| 中断批次处理 | 保留并支持断点续检，直到用户继续或放弃 |
| 第一阶段是否复制原图 | 只记录原始路径，不复制原图 |
| 第一阶段是否做原图哈希去重 | 否，保留扩展字段 |
| 热力图格式 | 无损 PNG |
| 保存范围 | 保存整个检测批次，不支持只保存部分图片 |
| 批次名称和备注 | 需要 |
| 已保存批次是否允许删除 | 允许，由用户明确触发 |
| 磁盘载入 | 支持从文件选择器选择批次清单并载入查看 |

## 5. 核心概念

### 5.1 检测批次

一次点击“开始检测”产生一个检测批次。无论输入是一张图片还是一个包含大量图片的文件夹，都属于一次批次。

检测开始时必须立即生成全局唯一的 `run_id`。推荐使用 UUID，不使用文件夹路径、开始时间或批次名称作为唯一标识。

示例：

```text
5dbd0f3a-bdaa-4bc4-85c7-6c0a9adfca90
```

批次负责记录：

- 输入来源
- 使用的模型及模型文件哈希
- 检测参数快照
- 开始、结束和保存时间
- 批次状态
- 结果统计
- 用户备注

### 5.2 检测条目

批次中的每张输入图片对应一个检测条目。

每个条目必须具有全局唯一的 `result_id`，并通过 `run_id` 关联到所属批次。

```text
一个检测批次 inspection_run
└── 多个检测条目 inspection_item
```

检测条目负责记录：

- 输入图片在批次中的固定顺序
- PENDING、PROCESSING、SUCCESS、FAILED 处理状态
- 原图信息
- 成功或失败状态
- 检测等级
- 异常分数
- 推理耗时
- 缺陷面积
- 热力图路径
- 错误信息

### 5.3 文件资源

以下内容属于文件资源，不直接作为二进制大对象存入 SQLite：

- 原始图片副本
- 热力图
- 缩略图
- 后续可能增加的掩膜图或叠加图

数据库只记录资源路径、文件类型、文件大小、文件哈希等元数据。

## 6. 总体存储架构

第一阶段采用“SQLite + 本地文件系统”的组合。

```text
Qt 客户端
├── SQLite
│   ├── 检测批次
│   └── 检测条目
└── 文件系统
    ├── 热力图
    ├── 缩略图
    └── 可选的原图副本
```

SQLite 负责：

- 查询和筛选
- 批次与条目关系
- 状态管理
- 检测参数和统计信息
- 防止重复保存

文件系统负责：

- 保存大尺寸图片
- 避免数据库快速膨胀
- 支持按需加载
- 保存可从磁盘重新载入批次的清单文件

## 7. 文件目录设计

建议将数据库和文件资源统一放在程序管理目录中：

```text
data/
└── persistence/
    ├── gluttony.db
    └── runs/
        └── {run_id}/
            ├── batch.json
            ├── items.jsonl
            ├── heatmaps/
            │   └── {result_id}.png
            ├── thumbnails/
            │   └── {result_id}.webp
            └── originals/
                └── {asset_id}.{extension}
```

第一阶段可以不创建 `originals` 中的文件，只在数据库中记录原图原始路径。

`batch.json` 是已保存批次的磁盘入口文件，`items.jsonl` 是逐行保存检测条目的明细文件。它们用于：

- 通过文件选择器定位一个已保存批次
- 校验批次 ID、结构版本和资源路径
- 在本地数据库索引丢失时重新导入批次元数据
- 将批次从其他磁盘位置载入当前客户端

这两个文件只在批次正式保存时生成。它们不包含完整图片二进制：

- `batch.json` 保存批次元数据、统计信息、明细文件名、条目数量和明细文件哈希。
- `items.jsonl` 每行保存一个检测条目，允许逐行生成和逐行载入。

不把所有检测条目放进 `batch.json` 的一个大数组，是为了避免载入大型批次时一次性占用大量内存。原图仍然使用检测时记录的绝对路径；如果原图已移动或删除，载入后允许只查看热力图。

不建议把文件物理目录分成 `drafts` 和 `results`。如果保存时移动整个批次目录，可能出现数据库状态已经更新但文件移动失败，或者文件已经移动但数据库更新失败的问题。

所有批次文件始终放在 `runs/{run_id}` 下，由数据库中的状态决定它属于草稿还是正式历史记录。

`inspection_run.storage_path` 用于标识批次目录。检测条目中的热力图和缩略图路径必须相对于这个批次目录保存，例如：

```text
heatmaps/{result_id}.png
```

本机新建批次的 `storage_path` 指向：

```text
data/persistence/runs/{run_id}
```

从其他磁盘位置载入批次时，`storage_path` 可以指向用户选择的外部批次目录。资源相对路径不能包含跳出批次目录的 `..` 路径。

## 8. 批次状态设计

### 8.1 状态定义

| 状态 | 含义 |
|---|---|
| `RUNNING` | 批次正在检测 |
| `DRAFT` | 检测已经结束，正在等待用户决定保存或放弃 |
| `SAVED` | 用户已经确认保存，可作为正式历史记录 |
| `INTERRUPTED` | 程序异常退出或任务未正常结束，可以断点续检 |

单张图片的成功或失败由检测条目状态表示，不需要因为一张图片失败就把整个批次标记为失败。

### 8.2 正常状态流转

```text
开始检测
    ↓
RUNNING
    ↓ 检测正常结束
DRAFT
    ↓ 用户点击保存
SAVED
```

### 8.3 异常状态流转

```text
RUNNING
    ↓ 程序异常退出
INTERRUPTED
    ├── 用户继续检测 → RUNNING
    └── 用户放弃 → 删除记录和关联文件
```

中断批次不能直接保存为完整批次。用户需要继续完成剩余检测，或者明确放弃整个批次。

### 8.4 放弃草稿

用户主动放弃 `DRAFT` 或 `INTERRUPTED` 批次时：

1. 删除批次中的检测条目。
2. 删除批次记录。
3. 删除该批次目录中的热力图和缩略图。
4. 删除仅由该批次拥有的原图副本。

`DISCARDED` 不作为第一阶段长期保留状态。放弃完成后，相关业务数据应不存在。

正常完成的 `DRAFT` 不长期保留。如果用户不保存、关闭批次或退出程序，应提示确认并直接删除草稿记录及其关联文件。`INTERRUPTED` 是断点续检所需的恢复数据，不适用“未保存即删除”规则。

## 9. 业务流程

### 9.1 开始检测

用户点击“开始检测”后，系统必须：

1. 生成新的 `run_id`。
2. 创建检测批次记录。
3. 将批次状态设置为 `RUNNING`。
4. 保存模型和检测参数快照。
5. 扫描并固定本次检测的完整输入文件清单。
6. 按输入顺序为每张图片创建状态为 `PENDING` 的检测条目。
7. 在同一个事务中写入输入清单和批次总数。
8. 创建 `runs/{run_id}` 目录。
9. 启动图片生产和推理线程。

必须先创建批次并完整保存输入清单，再开始处理第一张图片。不能只保存已经完成的结果，否则程序中断后无法准确知道还有哪些图片尚未处理。

### 9.2 单张图片检测完成

每张图片完成推理后，系统必须：

1. 按顺序取得一个 `PENDING` 条目。
2. 将条目状态更新为 `PROCESSING`。
3. 使用条目创建时已经生成的 `result_id`。
4. 将 PNG 热力图写入该批次目录。
5. 确认热力图文件写入成功。
6. 将检测条目更新为 `SUCCESS`。
7. 更新批次的已完成数量和分类统计。
8. 向 UI 发送轻量结果信息。
9. 释放不再需要的完整图像数据。

检测条目必须逐条写入，不得等整个批次结束后一次性写入。

### 9.3 单张图片检测失败

单张图片加载或推理失败时：

1. 不终止整个批次。
2. 将对应的 `PROCESSING` 条目更新为 `FAILED`。
3. 保存原图路径、顺序号和错误信息。
4. 增加批次的失败数量。
5. 继续处理后续图片。

失败条目不要求具有检测等级、异常分数或热力图。

### 9.4 批次检测完成

所有图片处理结束后，系统必须：

1. 将批次状态从 `RUNNING` 更新为 `DRAFT`。
2. 写入完成时间。
3. 写入最终统计信息。
4. 在 UI 中提供“保存”和“放弃”操作。

批次只有在所有条目都处于 `SUCCESS` 或 `FAILED` 时才能进入 `DRAFT`。

### 9.5 用户保存批次

用户点击“保存”时：

1. 使用现有 `run_id` 查找批次。
2. 将状态从 `DRAFT` 更新为 `SAVED`。
3. 仅在尚未保存时写入 `saved_at`。
4. 要求用户填写批次名称；备注可以为空。
5. 流式生成或更新 `runs/{run_id}/items.jsonl`。
6. 生成或更新 `runs/{run_id}/batch.json`。
7. 不重新插入检测条目。
8. 不重新生成热力图。
9. 不创建新的 `run_id`。

保存的业务含义是：

> 将已经落盘的检测草稿确认成需要长期保留的历史记录。

保存并不是此时才第一次把所有结果写入数据库或磁盘。

用户保存的是整个批次，不提供只保存部分检测条目的操作。

### 9.6 用户查看历史结果

用户打开已保存批次时：

1. 首先加载批次元数据和分页后的检测条目。
2. 不一次性读取全部热力图。
3. 用户点击某一条记录后，再根据路径加载对应原图和热力图。
4. 切换记录时释放上一张不再显示的完整图片。
5. 文件不存在时显示明确的缺失状态，不导致程序崩溃。

### 9.7 中断批次续检

程序启动时发现上次遗留的 `RUNNING` 批次后，应先将其标记为 `INTERRUPTED`。

继续检测前必须：

1. 将中断时处于 `PROCESSING` 的条目恢复为 `PENDING`。
2. 检查原模型文件是否仍然存在。
3. 校验当前模型文件哈希与批次记录中的 `model_hash` 是否一致。
4. 恢复批次保存的阈值和热力图参数，不能使用当前 UI 中的新参数。
5. 按 `sequence_no` 查询所有 `PENDING` 条目。
6. 检查待处理原图的文件大小和修改时间是否与输入清单一致。
7. 将批次从 `INTERRUPTED` 更新为 `RUNNING`。
8. 从第一个未完成条目开始继续检测。

续检必须使用与原批次相同的模型内容和检测参数。如果模型不存在或哈希不一致，应阻止续检并提示用户重新提供完全相同的模型。使用不同模型继续处理同一个批次会使批次内部结果不可比较，因此不允许这样做。

如果续检时某张原图已经移动、删除或内容特征与输入清单不一致，应将该条目更新为 `FAILED`，记录具体原因，然后继续处理其他条目。第一阶段使用文件大小和修改时间检查变化；后续可以启用完整 SHA-256 校验。

### 9.8 从磁盘载入已保存批次

客户端应提供“载入批次”操作，允许用户通过文件选择器选择：

```text
batch.json
```

载入流程：

1. 读取并解析批次清单。
2. 校验清单结构版本、`run_id` 和必需字段。
3. 校验 `items.jsonl` 文件哈希。
4. 逐行读取 `items.jsonl`，校验条目数量和必需字段。
5. 检查热力图相对路径是否位于所选批次目录内。
6. 如果当前数据库已经存在相同 `run_id`，直接打开已有批次，不重复导入。
7. 如果数据库中不存在该 `run_id`，分批次事务幂等导入批次和检测条目。
8. 将导入批次标记为 `SAVED`。
9. 按需加载原图和热力图进行查看。

如果原图路径已经失效，仍然允许载入批次并查看存在的热力图。批次清单或热力图文件缺失时，应显示具体问题，不能部分静默导入。

为防止路径穿越，清单中的热力图和缩略图相对路径解析后必须仍位于所选批次目录中。

### 9.9 删除已保存批次

用户可以删除 `SAVED` 批次。删除前必须明确提示：

- 将删除数据库中的批次和检测条目。
- 对于本程序管理的批次，将删除该批次目录中的 `batch.json`、`items.jsonl`、热力图和缩略图。
- 对于从外部磁盘载入的批次，默认只从当前数据库索引中移除，不删除外部目录。
- 不会删除原始绝对路径指向的用户原图。
- 删除操作不可通过普通历史列表恢复。

删除范围必须由确定的 `run_id` 和受管理的批次目录共同限定。

## 10. 重复与幂等规则

### 10.1 重复保存同一批次

相同的 `run_id` 永远表示同一批次。

第一次保存：

```text
run_id=A
DRAFT → SAVED
```

再次保存：

```text
run_id=A
仍然是 SAVED
不创建新批次
不重复插入检测条目
```

UI 可以在保存成功后禁用保存按钮，但数据库主键、唯一约束和更新语义才是最终保障。

### 10.2 重新检测相同图片

用户再次点击“开始检测”时，无论输入路径是否相同，都必须生成新的 `run_id`。

```text
第一次检测：run_id=A
第二次检测：run_id=B
```

两个批次都需要保留，因为以下内容可能发生变化：

- 模型或模型版本
- 模型文件内容
- REVIEW 和 NG 阈值
- 热力图透明度
- 输入图片内容
- 程序版本
- 检测时间
- 推理结果

不得使用文件夹路径作为检测批次唯一标识。

### 10.3 同一批次中的重复图片

第一阶段不自动删除重复输入。

例如用户输入：

```text
A.png
A.png
B.png
```

系统可以把它们作为三个检测条目处理：

```text
sequence_no=1 → A.png
sequence_no=2 → A.png
sequence_no=3 → B.png
```

因此，不应将 `(run_id, source_file_path)` 设置为唯一约束。

第一阶段建议使用 `(run_id, sequence_no)` 唯一标识批次中的输入位置。

### 10.4 原图去重

第一阶段只预留 `source_file_hash` 字段，不实现物理文件去重。

后续需要归档原图时，可以使用 SHA-256 判断文件内容是否相同，使不同检测批次引用同一份原图资源。热力图不能仅根据原图进行去重，因为不同模型和参数可能生成不同热力图。

### 10.5 重复载入同一磁盘批次

`batch.json` 中的 `run_id` 是载入幂等键。

同一个批次清单被重复选择时：

- 不创建新的 `run_id`。
- 不重复插入检测条目。
- 如果数据库已经存在该批次，直接打开。
- 如果磁盘清单与数据库中相同 `run_id` 的内容冲突，应停止载入并提示冲突，不能静默覆盖。

## 11. 逻辑数据模型

第一阶段至少需要两个核心数据对象：

- `inspection_run`
- `inspection_item`

后续可以增加：

- `model_version`
- `asset`
- `schema_version`

### 11.1 检测批次 inspection_run

| 字段 | 类型建议 | 是否必需 | 说明 |
|---|---|---|---|
| `run_id` | UUID/Text | 是 | 批次主键 |
| `name` | Text | 是 | 用户保存时填写的批次名称 |
| `status` | Text/Enum | 是 | RUNNING、DRAFT、SAVED、INTERRUPTED |
| `source_type` | Text/Enum | 是 | SINGLE_IMAGE 或 FOLDER |
| `source_path` | Text | 是 | 用户选择的图片或文件夹 |
| `storage_path` | Text | 是 | 当前批次目录路径 |
| `storage_origin` | Text/Enum | 是 | MANAGED 或 EXTERNAL |
| `model_path` | Text | 是 | 模型路径快照 |
| `model_hash` | Text | 否 | 模型文件 SHA-256 |
| `model_format` | Text/Enum | 是 | ONNX 或 OPENVINO |
| `review_threshold` | Real | 是 | REVIEW 阈值快照 |
| `ng_threshold` | Real | 是 | NG 阈值快照 |
| `heatmap_alpha` | Real | 是 | 热力图透明度快照 |
| `started_at` | DateTime | 是 | 开始时间 |
| `completed_at` | DateTime | 否 | 检测结束时间 |
| `saved_at` | DateTime | 否 | 用户确认保存时间 |
| `total_count` | Integer | 是 | 输入总数 |
| `completed_count` | Integer | 是 | 已处理数量 |
| `failed_count` | Integer | 是 | 失败数量 |
| `ok_count` | Integer | 是 | OK 数量 |
| `review_count` | Integer | 是 | REVIEW 数量 |
| `ng_count` | Integer | 是 | NG 数量 |
| `average_score` | Real | 否 | 成功结果的平均异常分数 |
| `note` | Text | 否 | 用户备注 |

模型路径和阈值必须保存为本次检测的快照。用户以后修改界面参数时，历史批次仍然需要能够解释当时的判定依据。

对于 ONNX，`model_hash` 是 `.onnx` 文件哈希；对于 OpenVINO IR，`model_hash` 必须能够同时代表 `.xml` 和对应 `.bin` 的内容，不能只计算 XML 文件。

### 11.2 检测条目 inspection_item

| 字段 | 类型建议 | 是否必需 | 说明 |
|---|---|---|---|
| `result_id` | UUID/Text | 是 | 检测条目主键 |
| `run_id` | UUID/Text | 是 | 所属批次外键 |
| `sequence_no` | Integer | 是 | 在批次中的输入顺序 |
| `source_file_name` | Text | 是 | 原始文件名 |
| `source_file_path` | Text | 是 | 原始绝对路径 |
| `source_file_size` | Integer | 是 | 建立输入清单时的文件大小 |
| `source_modified_at` | DateTime | 是 | 建立输入清单时的修改时间 |
| `source_file_hash` | Text | 否 | 原图 SHA-256，第一阶段可为空 |
| `status` | Text/Enum | 是 | PENDING、PROCESSING、SUCCESS、FAILED |
| `detection_level` | Text/Enum | 否 | OK、REVIEW、NG |
| `score` | Real | 否 | 异常分数 |
| `inference_ms` | Integer | 否 | 推理耗时 |
| `defect_area` | Integer | 否 | 缺陷面积 |
| `heatmap_path` | Text | 否 | 热力图相对路径 |
| `thumbnail_path` | Text | 否 | 缩略图相对路径 |
| `error_message` | Text | 否 | 失败原因 |
| `created_at` | DateTime | 是 | 输入条目创建时间 |
| `updated_at` | DateTime | 是 | 最近一次状态更新时间 |
| `attempt_count` | Integer | 是 | 包含续检在内的处理尝试次数 |

建议的数据约束：

- `result_id` 为主键。
- `run_id` 必须引用存在的检测批次。
- `(run_id, sequence_no)` 必须唯一。
- 删除批次时，应同时删除其检测条目。
- `status=PENDING` 或 `PROCESSING` 时允许结果字段为空。
- `status=FAILED` 时允许检测结果字段为空。
- `status=SUCCESS` 时必须具有检测等级和异常分数。

检测条目必须在批次开始前根据完整输入清单预先创建，而不是在推理完成后才首次创建。这是断点续检能够可靠工作的基础。

### 11.3 磁盘批次清单

`batch.json` 和 `items.jsonl` 是已保存批次的可移植磁盘索引，不代替 SQLite，但可以用于从磁盘重新建立数据库索引。

`batch.json` 至少包含：

- 清单格式和结构版本
- `run_id`
- 批次名称和备注
- 批次时间信息
- 模型格式、模型哈希和模型路径快照
- 检测参数快照
- 批次统计
- `items.jsonl` 的相对文件名
- 检测条目总数
- `items.jsonl` 的文件大小和 SHA-256

`items.jsonl` 每行是一个独立 JSON 对象，至少包含：

- `result_id`
- `sequence_no`
- 原图路径和原图文件信息
- 条目状态和检测结果
- 热力图、缩略图相对路径
- 错误信息和时间信息

清单不得包含：

- 完整图片的 Base64 内容
- 任意可执行命令
- 数据库连接信息
- 超出批次目录的可写目标路径

保存磁盘清单时应：

1. 从 SQLite 分页查询检测条目。
2. 逐行写入 `items.jsonl.tmp`，不一次性加载全部条目。
3. 完成后计算文件大小和 SHA-256。
4. 写入 `batch.json.tmp`。
5. 原子重命名 `items.jsonl.tmp` 为 `items.jsonl`。
6. 原子重命名 `batch.json.tmp` 为 `batch.json`。
7. 最后将数据库批次状态更新为 `SAVED`。

任一步骤失败时，批次保持 `DRAFT`，并删除不完整的清单临时文件。

## 12. 内存管理要求

当前用于结果列表的记录对象不应长期持有完整原图或完整热力图。

长期保留的轻量信息包括：

- `result_id`
- `run_id`
- 文件名
- 检测等级
- 异常分数
- 推理耗时
- 缺陷面积
- 原图路径
- 热力图路径

UI 显示策略：

1. 表格只显示文本数据或低分辨率缩略图。
2. 用户点击某一行时，才加载完整原图和热力图。
3. 切换记录时释放上一张完整图片。
4. 如需缓存，只允许使用固定容量的最近最少使用缓存。
5. 缓存大小必须与图片总数量无关，例如最多缓存最近 5 张。

即使检测十万张图片，完整图片的内存占用也应保持在固定范围内。

## 13. 文件与数据库一致性

图片文件和 SQLite 不能天然组成同一个事务，因此需要明确写入顺序。

### 13.1 推荐写入顺序

1. 将热力图写入带 `.tmp` 后缀的临时文件。
2. 确认临时文件完整写入。
3. 将临时文件原子重命名为正式文件名。
4. 在数据库事务中将检测条目更新为 `SUCCESS` 并更新批次统计。
5. 数据库写入失败时，删除刚生成且尚未被引用的正式文件。

```text
{result_id}.png.tmp
    ↓ 文件写入成功
{result_id}.png
    ↓ 数据库事务成功
检测条目持久化完成
```

程序启动时应清理超过一定时间且没有数据库记录引用的 `.tmp` 文件。

### 13.2 文件丢失处理

如果数据库记录存在但文件已经被用户手动删除：

- 历史列表仍应正常打开。
- 对应图片位置显示“文件缺失”。
- 日志记录缺失路径。
- 不因单个文件缺失导致整个批次加载失败。

### 13.3 孤立文件处理

如果文件存在但数据库中没有引用：

- 新生成且数据库事务失败的文件应立即清理。
- 程序启动或维护操作可以扫描并清理长期孤立文件。
- 第一阶段只自动清理明确位于受管理目录内的文件。

## 14. 草稿恢复与清理策略

### 14.1 正常关闭

程序关闭时，如果存在 `DRAFT` 批次，应提示用户：

- 保存
- 放弃

用户不保存时直接删除 `DRAFT` 批次及其关联文件，不提供“保留普通草稿稍后处理”选项。

如果存在正在检测的 `RUNNING` 批次，正常退出前应先停止工作线程并将批次标记为 `INTERRUPTED`，以便下次断点续检。

### 14.2 异常关闭

程序下次启动时：

1. 查找状态为 `RUNNING` 的批次。
2. 将其视为异常中断。
3. 更新为 `INTERRUPTED`。
4. 显示已完成数量和总数量。
5. 允许用户继续检测或放弃整个中断批次。

### 14.3 自动清理

清理策略：

- `SAVED` 批次长期保留，允许用户明确删除。
- `DRAFT` 批次未被保存时直接删除，不设置 7 天保留期。
- `INTERRUPTED` 批次为断点续检数据，不自动按草稿规则删除。
- 用户必须对 `INTERRUPTED` 批次执行“继续检测”或“放弃”。
- 自动清理不得删除 `SAVED` 或仍待续检的 `INTERRUPTED` 批次。

## 15. 功能需求

### FR-01 创建检测批次

用户开始检测时，系统必须创建唯一检测批次，并将状态设置为 `RUNNING`。

### FR-02 逐条持久化

每张图片检测完成后，系统必须立即保存检测结果和热力图，不得等待整个批次结束。

### FR-03 限制内存占用

系统不得在检测结果集合中长期保存所有完整原图和热力图。

### FR-04 保存批次

用户保存草稿时，系统必须将批次状态修改为 `SAVED`。

### FR-05 保存幂等

同一个批次被重复保存时，不得创建重复批次或重复检测条目。

### FR-06 重新检测

用户重新执行检测时，系统必须创建新的检测批次，即使输入图片与历史批次完全相同。

### FR-07 放弃草稿

用户放弃草稿时，系统必须删除草稿数据库记录及其关联文件。

### FR-08 异常恢复

程序启动时，系统必须识别未正常结束的 `RUNNING` 批次，并允许用户继续检测或放弃。

### FR-09 历史查看

用户必须能够打开一个已保存批次，查看批次汇总和每张图片的检测结果。

### FR-10 失败记录

单张图片检测失败时，不得导致整个批次丢失；系统必须记录对应图片和失败原因。

### FR-11 文件缺失容错

原图或热力图文件缺失时，系统必须显示缺失状态，并继续展示其他有效结果。

### FR-12 草稿清理

用户不保存完整批次时，系统必须直接删除草稿和关联文件。

### FR-13 断点续检

系统必须在检测开始前保存完整输入清单，并允许中断批次使用相同模型和参数继续处理所有未完成条目。

### FR-14 磁盘载入

系统必须允许用户选择已保存批次的 `batch.json`，校验并幂等载入批次进行查看。

### FR-15 批次名称与备注

用户保存整个批次时必须填写批次名称，并可以填写备注。

### FR-16 删除已保存批次

用户必须能够明确删除已保存批次。删除操作不得影响受管理目录之外的原始图片。

## 16. 非功能需求

### 16.1 性能

- 检测条目数量增加时，完整图片内存占用不得线性增长。
- 历史结果列表需要支持分页或分段读取。
- 数据库写入不得长时间阻塞 UI 线程。
- 单条结果持久化失败不得终止后续图片检测。

### 16.2 可靠性

- 重复保存必须是幂等操作。
- 每张图片完成后应具备可恢复记录。
- 数据库更新批次统计和插入检测条目时应使用事务。
- 受管理目录之外的用户文件不得被自动删除。

### 16.3 可维护性

- 数据库访问、文件存储和 UI 展示职责应分离。
- 数据库结构需要具有版本号。
- 后续表结构变化应通过迁移完成，不直接假定所有用户都是全新数据库。
- 状态和枚举值应集中定义，避免各模块使用不同字符串。

### 16.4 可扩展性

设计应允许后续增加：

- 模型版本表
- 文件资源表
- 原图去重
- 用户与操作记录
- PostgreSQL
- 对象存储
- 远程历史查询

## 17. 验收场景

### AC-01 重复保存

1. 检测 100 张图片。
2. 点击保存。
3. 再次触发保存。
4. 数据库中只有 1 个检测批次。
5. 数据库中只有 100 个检测条目。

### AC-02 重复检测

1. 检测文件夹 A 并保存。
2. 再次检测文件夹 A 并保存。
3. 数据库中存在 2 个不同的 `run_id`。
4. 两个批次分别保留自己的参数和检测结果。

### AC-03 大批量检测

1. 检测至少 10,000 张图片。
2. 每张图片完成后，数据库和文件系统均存在对应结果。
3. 内存中的完整热力图数量保持在固定上限内。
4. 检测数量增加时，完整图片内存占用不持续线性增长。

### AC-04 中途崩溃

1. 开始检测 1,000 张图片。
2. 第 326 张完成后强制关闭程序。
3. 再次启动程序。
4. 系统识别未完成批次。
5. 用户能够查看已完成的 326 条结果。
6. 第 327 张及之后的条目仍然处于待处理状态。
7. 用户继续检测后，系统从第一个未完成条目开始处理。
8. 已完成的 326 条结果不会被重复检测或重复写入。

### AC-05 放弃草稿

1. 完成一次检测但不保存。
2. 点击放弃。
3. 对应批次和检测条目从数据库中删除。
4. 对应热力图和缩略图从受管理目录中删除。
5. 受管理目录之外的原始图片不受影响。

### AC-06 按需加载

1. 打开一个包含 10,000 条记录的历史批次。
2. 系统不一次性加载 10,000 张完整热力图。
3. 点击某一条记录时才加载对应原图和热力图。
4. 切换记录后可以释放上一张完整图片。

### AC-07 单张失败

1. 批次中包含一张损坏图片。
2. 其他图片继续正常检测。
3. 损坏图片记录为 `FAILED`。
4. 失败条目保存具体错误信息。

### AC-08 文件缺失

1. 保存一个检测批次。
2. 手动删除其中一张热力图。
3. 重新打开该批次。
4. 批次和其他条目仍然正常显示。
5. 缺失条目显示明确的文件缺失状态。

### AC-09 不保存即删除

1. 完成一个检测批次。
2. 在保存确认中选择不保存。
3. 数据库中不存在该批次和检测条目。
4. 受管理目录中不存在该批次的热力图和清单。

### AC-10 磁盘载入

1. 保存一个检测批次并生成 `batch.json` 和 `items.jsonl`。
2. 从当前数据库中删除该批次索引，但保留批次目录用于测试。
3. 通过文件选择器选择该 `batch.json`。
4. 系统成功校验并导入批次。
5. 用户可以查看检测结果和热力图。
6. 原图已删除时，系统仍能查看热力图。

### AC-11 重复载入

1. 连续两次选择同一个 `batch.json`。
2. 数据库中只有一个对应的 `run_id`。
3. 检测条目数量没有增加。

### AC-12 删除已保存批次

1. 保存一个检测批次。
2. 用户确认删除该批次。
3. 批次、检测条目、清单和热力图被删除。
4. 原始图片保持不变。

### AC-13 续检模型不一致

1. 中断一个正在运行的批次。
2. 替换原模型文件，使其哈希发生变化。
3. 尝试继续检测。
4. 系统阻止续检并提示模型内容不一致。
5. 已完成结果保持不变。

## 18. 分阶段实施建议

- 按已确认决策不保留未保存的普通草稿。

## 19. 已确认业务决策

以下决策已经确认：

1. 第一阶段只记录原图路径，不复制原图。
2. 原图移动或删除后，接受历史记录只能显示热力图。
3. 用户保存整个检测批次，不支持只保存部分图片。
4. 普通草稿未保存时直接删除，不设置 7 天保留期。
5. 中断批次需要支持断点续检。
6. 热力图使用无损 PNG。
7. 用户保存批次时需要填写名称，并允许填写备注。
8. 已保存批次允许由用户明确删除。
9. 用户可以从磁盘选择已保存批次并载入查看。

这些决定将作为下一阶段数据库结构和存储接口设计的约束，不应在实现时被隐式改变。
